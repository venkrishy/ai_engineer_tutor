A tutor that lives in the mailbox

A student gets a problem by email, sends a zip of code back, and receives a pass or a fail on the same thread. The note says what passed or what to fix. Pass moves them forward. Fail keeps them on the same problem. There is no website.

Self-Registration

There is no form. A student registers by writing to tutor@aiguru.dev. That first letter creates them, and the reply is problem 1. A zip on that first letter is ignored.

Coding Assignment and Grading Workflow

Each attempt is a submission that solves the coding assignment, emailed as one zip of 10 MB or less. The zip holds main.py at the top or inside a single folder. It is not graded on arrival. It waits with the others.

The backend grades the waiting assignments together, in one batch, and it does that in private. Each student has a daily cap on how many assignments they can submit. Their code runs on one model chosen ahead of time, and grading uses that same model and no other.

Inside a grade

This is the white box above, opened up. Ten graded tries are allowed in a UTC day. On the next one we say the cap is hit, and we do not start a room. If everyone waiting is already at the cap, the door stays shut.

Each zip gets its own room on that private network. The room cannot reach the public internet. We place the model key in the room. The student never receives it. The room runs for three minutes, then closes. The door is shared by the whole batch and deleted at the end, which stops the hourly charge.

The model does not decide the grade. A checker we wrote does. It runs the program against five tickets the student has not seen. Four of the five must pass. Our code writes the first line of the email: Pass, Fail, or Not graded. The model writes the explanation, and only on a pass or a fail.

A grade that already finished still counts, and it uses one of the ten tries. A timeout, a model error, or a crashed checker is not a fail, and it does not use a try. A second zip from a student whose room is already running is set aside. The reply asks them to send again after the result.

After the third failed try, unfinished letters are not graded and do not use a try. The door is still deleted.

Pass and fail

Pass

The checker finishes cleanly. The next problem rides along in the same reply, and the student moves forward one step.

Fail

Anything else the checker returns. The reply includes the checker’s notes, up to 8 KB. The same problem stays open.

Each attempt stands on its own. The previous zip is thrown away. After problem 3, the mail says the sequence is finished.

The three problems

All three are ticket triage. Each one adds a field. The tickets used for grading stay hidden. The email includes the instructions, the shape of the answer, and one sample ticket.

Problem The program must return
01 Classify The ticket id, and a label: bug, billing, access, or other.
02 Route Those, plus a priority (P1, P2, P3) and a queue. Bugs go to engineering, billing goes to billing, and the rest go to support.
03 Reply Those, plus a short customer reply. It must contain the ticket id, stay under 80 words, and say “refund” only when the ticket does.

Billing means charges, invoices, refunds, or payment. Access means login, password, or permissions. Bug means the product is broken. Everything else is other. P1 means work is blocked or money is wrong. P3 is a how-to. P2 is the rest.

The label, priority, and queue must match the answer key. The customer reply is checked against those rules, not against a canned paragraph. The program reads the ticket as JSON and prints one JSON object. It uses the Python standard library, calls the model with no randomness, and reads the key, the model name, and the region from the room around it.

Letters that are not a grade

  • No zip: we send the current problem again.
  • More than one attachment: we ask for a single zip.
  • The same letter arrives twice: we grade it once and reply once.
  • The grader times out, the model errors, or the checker crashes: we say it was not graded. That is not a fail, and it does not use a daily try.
  • The zone fails: we delete the door, pause, and try again, up to three times. After that, unfinished letters are not graded and do not use a daily try. A pass or a fail that already finished still counts.
  • After 10 graded tries in a UTC day: we stop and say the cap is hit. No room is started. A batch of only capped students does not open the door.
  • Mail after the last problem: we say the sequence is complete, and we do not grade.

The names on the blue boxes

Skip this if the pictures were enough. It is the same system, with the names an engineer would type. Everything runs in us-east-1. DNS for aiguru.dev stays at Cloudflare, and Cloudflare Email Routing and Email Sending stay off so they do not take the same MX and SPF records. The MX record points at SES. Bounces use bounce.aiguru.dev.

  • Problems live in this repo as folders: instructions, a rubric for the reply writer, a checker, and five hidden tickets.
  • The student card is a DynamoDB row: email, current problem, whether a grade is in flight, graded tries for the UTC day, last result, and message ids already handled.
  • The long-term key for the room sits in Secrets Manager. The model is Claude Sonnet 4.6 (us.anthropic.claude-sonnet-4-6). The program calls it with temperature 0.
  • The grading room is Code Interpreter on a private network, with no NAT gateway and no public internet.
  • The door is one interface VPC endpoint, in one subnet, with private DNS. The room’s permission may call this Sonnet profile and the same foundation model in us-east-1, us-east-2, and us-west-2, because the profile routes across those three. The door itself accepts only the profile and the us-east-1 model, and only from this account. The calls are invoke and converse, including the streaming forms.
  • Each zip gets a new room, limited to 3 minutes, then closed. The door is shared by the batch and deleted at the end.
  • While the door exists, AWS charges $0.01 per hour for that one zone. A door left up for a month is about $7.30. A short batch is a fraction of a cent, plus $0.01 per gigabyte through the door.

Until SES production access is granted, a reply can go only to a verified address, the SES mailbox simulator, or an address at a domain this account has already verified.

What this version leaves out

  • Slack, and any other channel besides email.
  • A website, a signup form, and an admin screen for uploading problems.
  • A model that picks a harder problem by reading the code. The order is fixed.
  • More skills after ticket triage. Those are more folders, added after one student finishes this ladder.
  • A second availability zone. Add it when real students are on the ladder. Until then a dead zone pauses grading, and after three tries the letter is not graded.
  • Leaving the door open between batches.
  • Sending or receiving the mail through Cloudflare. Cloudflare is DNS only.

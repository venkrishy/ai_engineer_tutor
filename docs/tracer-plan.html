A tutor that lives in the mailbox

A student gets a problem by email, sends a zip of code back, and receives a pass or a fail. Every automatic grade includes feedback on what passed or what to fix. Pass moves them to a harder problem. Fail keeps them on the same one. There is no website.

The route

Students write to tutor@aiguru.dev. Cloudflare holds the DNS for that domain. Amazon SES sends and receives the mail. Cloudflare Email Routing and Email Sending stay off, so they do not take the same MX and SPF records.

A small program, the clerk, decides what to do with each letter. Grading waits for a batch. The clerk opens one private door to Claude, grades whoever is waiting, and deletes the door. The student’s code can reach one Sonnet model through that door, and nothing else.

The door

The door is an interface endpoint in one availability zone. It is created only when a batch has someone under the daily cap, and deleted when that batch ends. Deleting it stops the hourly charge. Opening it takes a few minutes, which is why grading is a batch and not one letter at a time.

A grade that already finished still counts. A second zip from a student whose room is already running is discarded. The reply asks them to send again after the result.

The loop

  1. Someone emails tutor@aiguru.dev. The first letter creates that student. The reply is problem 1. A zip on that first letter is ignored.
  2. The student replies with one zip of 10 MB or less. The zip holds main.py, at the top or inside one folder.
  3. The zip waits for the next batch. The clerk opens the door, runs that program on five hidden tickets, and shuts the door when the batch is done. The program calls Claude with the key we inject. The student never receives the key.
  4. A checker, not Claude, marks the work. Four of the five tickets must pass.
  5. The reply is plain text on the same thread. The first line is Pass, Fail, or Not graded, written by code. Claude only writes the explanation on a pass or a fail.
  6. Fail keeps the same problem. Pass includes the next problem in that same email. After problem 3, the mail says the sequence is finished.

Pass and fail

Pass

The checker’s exit code is 0. The next instructions ride along in the same reply. The student moves forward one problem.

Fail

Any other exit code. The reply includes the checker’s notes, up to 8 KB. The same problem stays open.

Each attempt is graded on its own. The previous zip is thrown away.

The three problems

All three are ticket triage. Each one adds a field. The tickets used for grading stay hidden. The email includes the instructions, the output shape, and one sample ticket.

Problem The program must return
01 Classify The ticket id, and a label: bug, billing, access, or other.
02 Route Those, plus a priority (P1, P2, P3) and a queue. Bugs go to engineering, billing goes to billing, and the rest go to support.
03 Reply Those, plus a short customer reply. It must contain the ticket id, stay under 80 words, and say “refund” only when the ticket does.

Billing means charges, invoices, refunds, or payment. Access means login, password, or permissions. Bug means the product is broken. Everything else is other. P1 means work is blocked or money is wrong. P3 is a how-to. P2 is the rest.

The label, priority, and queue must match the answer key. The reply is checked against the rules above, not against a canned paragraph. The program reads the ticket as JSON on standard input and prints one JSON object. It uses the Python standard library, calls Bedrock with a temperature of 0, and reads the key, model, and region from the environment.

Letters that are not a grade

  • No zip: we send the current problem again.
  • More than one attachment: we ask for a single zip.
  • The same SES message arrives twice: we grade it once and reply once.
  • The grader times out, Bedrock errors, or the checker crashes: we say it was not graded. It is not a fail, and it does not use a daily attempt.
  • The zone fails: we delete the door, pause, and try again, up to three times. After that, unfinished letters are not graded and do not use a daily attempt. A pass or a fail that already finished still counts.
  • After 10 graded attempts in a UTC day: we stop and say the cap is hit. No grading room is started, and a batch of only capped students does not open the door.
  • Mail after the last problem: we say the sequence is complete and do not grade.

Where each thing lives

Everything is in us-east-1. DNS for aiguru.dev stays at Cloudflare. The MX record points at SES, and SES sends the replies. Bounces use bounce.aiguru.dev. A long-term Bedrock key for the room sits in Secrets Manager. The model is Claude Sonnet 4.6 (us.anthropic.claude-sonnet-4-6).

  • Problems live in this repo as folders: instructions, a rubric for the reply writer, a checker, and five hidden tickets.
  • The grading room is a Code Interpreter on a private network, with no NAT gateway and no public internet.
  • The door is one interface endpoint, in one subnet, with private DNS. The room’s role may call this Sonnet profile and the same foundation model in us-east-1, us-east-2, and us-west-2, because the profile routes across those three. The door itself accepts only the profile and the us-east-1 model, and only from this account. The calls are invoke and converse, including the streaming forms.
  • Each zip gets a new room, limited to 3 minutes, then closed. The door is shared by the batch and deleted at the end.
  • While the door exists, AWS charges $0.01 per hour for that one zone. A door left up for a month is about $7.30. A short batch is a fraction of a cent, plus $0.01 per gigabyte through the door.
  • Student rows live in DynamoDB: email, current problem, whether a grade is in flight, graded attempts for the UTC day, last result, and message ids already handled.

Until SES production access is granted, a reply can go only to a verified address, the SES mailbox simulator, or an address at a domain this account has already verified.

What this version leaves out

  • Slack, and any other channel besides email.
  • A website, a signup form, and an admin screen for uploading problems.
  • A model that picks a harder problem by reading the code. The order is fixed.
  • More skills after ticket triage. Those are more folders, added after one student finishes this ladder.
  • A second availability zone. Add it when real students are on the ladder. Until then a dead zone pauses grading, and after three tries the letter is not graded.
  • Leaving the Bedrock door open between batches.
  • Sending or receiving the mail through Cloudflare. Cloudflare is DNS only.
